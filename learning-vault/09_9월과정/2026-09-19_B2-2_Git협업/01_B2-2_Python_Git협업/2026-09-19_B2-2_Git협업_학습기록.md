## 1. 이 미션에서 실제로 배운 핵심

이번 미션의 본질은 Python 유틸 함수를 만드는 것이 아니었다. 핵심은 다음 흐름을 실제 팀 작업으로 반복하는 것이었다.

```text
Issue
  ↓
작업 브랜치
  ↓
코드·문서 수정
  ↓
commit
  ↓
push
  ↓
Pull Request
  ↓
다른 팀원의 Review
  ↓
작성자의 수정·답변
  ↓
Approve
  ↓
main Merge
```

중요한 것은 각 단계가 단순 형식이 아니라 **서로 다른 실패를 막는 안전장치**라는 점이다.

- Issue: 무엇을 해야 하는지 먼저 고정한다.
- Branch: 다른 사람의 안정된 작업과 내 작업을 분리한다.
- Commit: 변경을 작은 이력 단위로 남긴다.
- PR: main에 합치기 전에 변경 이유와 결과를 공개한다.
- Review: 작성자가 놓친 버그·위험·불일치를 다른 사람이 찾는다.
- Merge: 검토된 변경만 공유 기준선에 반영한다.
- 문서 기록: 나중에 같은 문제를 재현하고 설명할 수 있게 한다.

## 2. Git의 가장 중요한 내부 모델

### 2.1 Commit은 스냅샷 + 부모를 가진 기록이다

commit은 단순한 “저장 버튼”이 아니다. 특정 시점의 프로젝트 상태와 이전 commit과의 관계를 가진 Git 객체다.

```text
A ← B ← C
```

`C`는 이전 commit `B`를 부모로 가진다.

그래서 Git은 파일 이름만 보는 것이 아니라 **commit 그래프 전체**를 이용해서 branch와 merge 관계를 추적한다.

---

### 2.2 Branch는 프로젝트 복사본이 아니라 commit을 가리키는 포인터다

초보 단계에서 가장 중요한 오해 중 하나다.

```text
A ← B ← C
        ↑
       main
```

여기서 `main`은 파일 전체를 별도로 저장한 거대한 사본이 아니라 **commit C를 가리키는 이름표에 가깝다.**

새 commit을 만들면:

```text
A ← B ← C ← D
            ↑
           main
```

처럼 branch pointer가 앞으로 이동한다.

따라서 branch를 많이 만드는 것은 저장소를 여러 번 복사하는 것과 다르다.

---

### 2.3 HEAD는 “지금 내가 어디에서 작업하는지”를 가리킨다

보통 HEAD는 현재 checkout/switch한 branch를 가리킨다.

```bash
git switch feature/example
```

를 실행하면 작업 기준이 `feature/example`로 이동한다.

확인:

```bash
git branch --show-current
```

또는:

```bash
git status
```

---

### 2.4 `origin/main`은 내 로컬 `main`과 다르다

- `main`: 내 컴퓨터의 로컬 branch
- `origin/main`: 마지막으로 원격 상태를 확인했을 때 기억하고 있는 원격 `main`

원격 상태 갱신:

```bash
git fetch origin
```

즉 `origin/main`은 GitHub 서버 그 자체가 아니라 **로컬 Git이 기억하는 원격 추적 포인터**다.

## 3. GitHub Flow란 무엇인가

GitHub Flow는 실제로 쓰이는 협업 전략이다.

가장 단순하게 압축하면:

```text
main
 ↑
PR
 ↑
feature/*
```

작업 순서:

```text
1. main에서 작업을 시작한다.
2. feature branch를 만든다.
3. 작업하고 commit한다.
4. branch를 push한다.
5. PR을 연다.
6. 다른 사람이 review한다.
7. 필요한 수정 후 approve를 받는다.
8. main에 merge한다.
```

### 왜 필요한가

여러 명이 모두 main에서 직접 작업하면 다음 문제가 생긴다.

- 미완성 코드가 곧바로 공유된다.
- 누가 어떤 목적의 변경을 했는지 추적하기 어렵다.
- 리뷰할 시점이 사라진다.
- 여러 작업이 섞여 되돌리기 어려워진다.

GitHub Flow에서는 main을 상대적으로 안정된 상태로 유지하고, 작업을 짧은 branch 단위로 격리한다.

---

## 4. GitHub Flow와 Git Flow의 차이

이름이 비슷하지만 다른 branching strategy다.

### GitHub Flow

```text
feature → PR → main
```

장기 branch가 단순하다.

### 전통적인 Git Flow

```text
feature
   ↓
develop
   ↓
release
   ↓
main
```

추가로 `hotfix/*` 같은 branch를 별도로 운용하기도 한다.

### 핵심 차이

| 항목 | GitHub Flow | Git Flow |
|---|---|---|
| 장기 branch | 보통 `main` 중심 | `main`, `develop` |
| release branch | 보통 없음 | 사용 |
| hotfix branch | 별도 규칙 없음 | 명시적 사용 |
| 복잡도 | 낮음 | 높음 |
| 짧은 팀 프로젝트 | 적합 | 과할 수 있음 |
| 자주 배포하는 웹 서비스 | 적합 | 경우에 따라 복잡함 |

이번 B2-2처럼 작은 팀이 짧은 작업을 PR로 검토하는 미션에는 GitHub Flow가 자연스럽다.

## 5. Issue와 PR의 역할을 구분하기

### Issue

**무엇을 해야 하는가**를 적는다.

예:

```text
목적: 뺄셈 함수 구현

완료 조건:
- subtract(10, 3) == 7
- 실행 예시 확인
```

### Pull Request

**그 일을 어떻게 수행했고, 왜 그렇게 했으며, 어떻게 검증했는가**를 적는다.

좋은 PR의 최소 구조:

```md
## 연결 이슈
Closes #12

## What
무엇을 바꿨는가

## Why
왜 필요한가

## How
무엇으로 검증했는가
```

### `Closes #12`

PR이 기본 branch에 merge되면 연결된 Issue를 자동으로 닫을 수 있다.

그래서:

```text
Issue = 요구사항
PR = 구현과 검증
```

으로 기억하면 쉽다.

## 6. Pull Request는 단순한 “합쳐주세요” 버튼이 아니다

PR은 팀원이 다음을 볼 수 있게 만드는 **검토 공간**이다.

- 어떤 파일이 바뀌었는가
- 어떤 줄이 추가·삭제됐는가
- 왜 바꿨는가
- 테스트했는가
- 다른 기능을 깨뜨릴 위험은 없는가

좋은 review는 단순히 다음처럼 쓰지 않는다.

```text
LGTM
좋아요
문제 없어 보입니다.
```

대신 **파일·라인·동작·위험 중 하나를 구체적으로 언급**한다.

예:

```text
Python의 / 연산은 0으로 나누면 기본적으로 ZeroDivisionError를 발생시킵니다.
여기서 ValueError를 별도로 발생시키면 호출 측의 예외 처리와 달라질 수 있으므로
표준 예외를 유지하는 편이 좋겠습니다.
```

이 미션에서 실제로 review가 코드 동작을 바꾼 사례가 있었다.  
즉 review는 예의를 위한 형식이 아니라 **작성자 혼자서는 놓친 문제를 발견하는 두 번째 검증 레이어**다.

## 7. 좋은 PR 상호작용의 기본 형태

가장 이상적인 흐름:

```text
리뷰어 문제 발견
   ↓
Comment / Request changes
   ↓
작성자 수정 commit
   ↓
작성자 답변
   ↓
리뷰어 재확인
   ↓
Approve
   ↓
Merge
```

여기서 중요한 것은 **Approve보다 수정 과정이 더 좋은 학습 증거**라는 점이다.

리뷰가 실제 행동을 바꾸지 않았다면 단순 확인에 가까울 수 있다.

## 8. Merge conflict는 왜 발생하는가

Git이 두 branch의 변경을 자동으로 합칠 수 없을 때 conflict가 발생한다.

예를 들어 동일한 시작 상태:

```text
practice = undecided
```

A가:

```text
practice = option_a
```

B가:

```text
practice = option_b
```

로 같은 줄을 수정했다면 Git은 어느 것이 의미상 옳은지 알 수 없다.

이때 Git은 사람이 판단하도록 conflict marker를 만든다.

```text
<<<<<<< HEAD
practice = option_b
=======
practice = option_a
>>>>>>> other-branch
```

의미:

- `<<<<<<< HEAD`: 현재 내가 작업 중인 쪽
- `=======`: 경계
- `>>>>>>>`: 병합하려는 상대쪽

해결은 단순히 marker를 지우는 것이 아니다.

먼저 다음을 결정해야 한다.

```text
한쪽만 유지?
양쪽 모두 유지?
둘을 새 형태로 재구성?
```

그 다음 marker를 제거하고 검증한다.

## 9. 충돌 해결 기본 흐름

```bash
git status
```

어떤 파일이 conflict인지 확인한다.

파일을 열어 marker를 확인하고 의도를 결정한다.

수정 후:

```bash
git add 충돌파일
git commit
```

필요한 기능 또는 문서 형식을 다시 검증한다.

### merge 자체를 취소하고 싶다면

```bash
git merge --abort
```

실습 중 시작 상태가 잘못됐거나 해결을 처음부터 다시 해야 할 때 사용한다.

## 10. `git commit --amend`

### 무엇인가

가장 최근 commit의 내용 또는 메시지를 바로잡을 때 사용한다.

예:

```bash
git commit --amend
```

중요한 점:

**기존 commit을 내부적으로 수정하는 것이 아니라 새 commit을 만든다.**

그래서 commit SHA가 바뀐다.

```text
before: 3b60279
after : 380c23a
```

### 왜 공유된 commit에서 위험한가

이미 push한 commit을 amend하면:

```text
local history ≠ remote history
```

가 된다.

일반 push가 non-fast-forward로 거절될 수 있고 force push가 필요해질 수 있다.

따라서:

- 로컬의 최근 commit 정리 → 적합
- 이미 팀과 공유된 commit → 매우 신중

---

## 11. `git reset --soft HEAD~1`

### 무엇인가

현재 branch pointer를 한 commit 뒤로 옮긴다.

```bash
git reset --soft HEAD~1
```

핵심:

- commit은 현재 branch에서 취소된 것처럼 보임
- 변경 내용은 유지
- staging 상태도 유지

즉:

```text
“commit만 다시 하고 싶다”
```

는 상황에 유용하다.

### 반드시 확인할 것

```bash
git status --short
```

`--soft` 실습에서 commit이 사라졌다는 것만 보면 절반만 검증한 것이다.  
**변경이 staged 상태로 유지됐는지까지 확인해야 한다.**

### 위험

공유 branch의 history를 reset하고 force push하면 다른 사람의 작업을 끊을 수 있다.

## 12. `git revert`

공유된 commit을 안전하게 취소할 때 많이 사용한다.

```bash
git revert <commit-sha>
```

reset과 다르게 기존 commit을 삭제하지 않는다.

예:

```text
A ← B ← C
```

C를 revert하면:

```text
A ← B ← C ← D
```

D가 C의 변경을 반대로 적용하는 새 commit이다.

따라서:

- 과거 history 보존
- 원래 commit도 보임
- 취소했다는 사실도 보임
- 공유된 branch에서 reset보다 안전한 경우가 많음

### 핵심 구분

```text
reset  = branch pointer를 과거로 이동
revert = 취소 변경을 새 commit으로 추가
```

## 13. `git stash`

아직 commit하지 않은 작업을 잠깐 치우고 다른 작업을 해야 할 때 사용한다.

```bash
git stash
```

보관 목록:

```bash
git stash list
```

복원:

```bash
git stash pop
```

### untracked 파일도 포함

```bash
git stash -u
```

또는:

```bash
git stash push -u
```

`-u`는 untracked 파일을 포함한다.  
ignored 파일까지 포함하는 옵션은 아니다.

---

## 14. `stash apply`와 `stash pop`

### apply

```bash
git stash apply stash@{0}
```

작업은 복원하지만 stash 항목은 유지한다.

장점:

```text
복원
→ 결과 확인
→ 문제 없으면 drop
```

이라는 안전한 흐름을 만들 수 있다.

삭제:

```bash
git stash drop stash@{0}
```

### pop

```bash
git stash pop
```

적용이 성공하면 해당 stash를 제거한다.

### 안전한 판단

복원 결과를 먼저 검증하고 싶다면:

```text
apply → 확인 → drop
```

흐름이 더 보수적이다.

---

## 15. stash에서 tracked와 untracked의 차이

### untracked 파일

Git이 아직 추적하지 않으므로 일반 stash에 포함되지 않을 수 있다.

```bash
git stash push -u -- 파일
```

### tracked 파일의 수정분

이미 commit에 존재하는 파일의 수정분은 `-u` 없이 stash할 수 있다.

```bash
git stash push -- 파일
```

stash 후 파일 자체가 없어지는 것이 아니라 **마지막 commit 상태로 돌아간다.**

## 16. SHA / Hash / Commit ID

Git에서 자주 보이는:

```text
e5fa1a6
944e17d
```

같은 값은 commit을 식별하는 hash의 축약 형태다.

### SHA

Secure Hash Algorithm 계열의 해시 알고리즘 이름이다.

### Hash

입력 데이터를 일정한 길이의 식별값으로 바꾸는 함수 또는 그 결과다.

Git에서는 commit, tree, blob 같은 객체를 hash로 식별한다.

그래서 SHA는 단순 일련번호가 아니다.  
객체 내용이 달라지면 hash도 달라진다.

`amend` 후 SHA가 바뀌는 이유도 새 commit 객체가 만들어졌기 때문이다.

## 17. Git graph를 읽는 법

```bash
git log --oneline --graph --all
```

branch와 merge 관계를 ASCII 그래프로 보여준다.

예:

```text

|\
| * feature commit
|/
* previous main commit
```

이 명령은 단순 보기용이 아니라 다음을 검증할 때 유용하다.

- merge commit이 존재하는가
- revert 원본과 취소 commit이 둘 다 남았는가
- conflict 실습의 부모 관계가 맞는가

## 18. `git show --remerge-diff`

merge conflict를 나중에 다시 분석할 때 유용한 명령이다.

```bash
git show --remerge-diff <merge-commit>
```

Git이 merge 당시의 양쪽 변경을 다시 구성해 conflict가 어떤 형태였는지 보여 줄 수 있다.

이번 실습에서 단순히 “충돌이 났다고 문서에 썼다”보다 **Git 객체와 부모 관계로 실제 충돌을 검증하는 것**이 훨씬 강한 증거라는 점을 배웠다.

## 19. `git diff`를 보는 습관

작업 전후에 최소한 다음 흐름을 반복한다.

```bash
git status
git diff
```

staging 후:


## 20. Branch Protection / Ruleset

팀 저장소의 `main`은 사람이 실수로 직접 push하지 못하게 보호할 수 있다.

이번 미션에서는 다음과 같은 규칙이 중요했다.

- PR을 통해서만 merge
- 최소 1명 Approve
- review conversation 해결
- force push 제한

이런 설정의 목적은 “사람을 못 믿어서”가 아니다.

**좋은 행동을 개인 기억이 아니라 시스템 기본값으로 만드는 것**이다.

---

# 21. reset / revert / stash / amend 한 번에 비교

| 명령 | 핵심 목적 | history | 파일 변경 | 공유 branch에서 |
|---|---|---|---|---|
| `commit --amend` | 최근 commit 수정 | 새 commit으로 교체 | 유지 가능 | 신중 |
| `reset --soft HEAD~1` | 최근 local commit 취소 | branch pointer 이동 | staged로 유지 | 위험 |
| `revert` | 공유 commit 취소 | 취소 commit 추가 | 반대 변경 적용 | 상대적으로 안전 |
| `stash` | 미커밋 작업 임시 보관 | commit history와 별개 | 임시 저장·복원 | 작업 전환에 사용 |

외우기보다 **history를 어떻게 바꾸는가**를 기준으로 구분한다.

# 22. 이번 미션에서 배운 AI 에이전트 협업 원칙

이 부분은 Git 명령만큼 중요했다.

## 22.1 에이전트가 공유 문서를 먼저 크게 고치면 충돌 비용이 커질 수 있다

여러 사람이 동시에 수정하는 파일:

```text
SUBMISSION.md
docs/troubleshooting-log.md
docs/conflict-resolution.md
README.md
```

은 충돌 위험이 높다.

특히 에이전트가 명세 전체를 읽고 미리 “완성본”을 만들면, 이후 사람이 실제 실습을 하면서 같은 파일을 다시 바꾸게 된다.

그 결과:

```text
사람 작업
+
에이전트 작업
+
다른 사람의 PR
=
반복 merge / conflict / 재정리
```

가 된다.

### 다음에는

공유 고충돌 문서는 가능한 한:

```text
single writer
```

원칙을 둔다.

또는:

```text
troubleshooting/
├── amend.md
├── reset.md
├── revert.md
└── stash.md
```

처럼 작업별 파일로 나눈 뒤 마지막에 index에서 합친다.

---

## 22.2 에이전트의 가장 좋은 역할은 “사실 생성자”보다 “감사자”다

AI가 대신할 수 있는 것:

- 요구사항 체크
- 파일 간 모순 찾기
- PR diff 검토
- 문서 초안
- 명령어 설명
- 테스트 명령 제안
- evidence index 정리

AI가 대신했다고 주장하면 안 되는 것:

- 사람이 실제로 명령을 입력했다는 사실
- 사람이 이해했다는 사실
- 타인 명의의 review
- 실제 현장 합의
- 존재하지 않는 hash·terminal output

따라서:

```text
AI = 증거 수집·검증·초안
사람 = 실제 행동·승인·최종 책임
```

구조가 안전하다.

---

## 22.3 내부 증거 장부와 외부 제출 문서를 분리한다

에이전트는 거짓말을 피하려고 다음을 많이 남긴다.

```text
미확인
PENDING
직접 실행 아님
증빙 부족
```

이 정보는 내부 감사 문서에는 매우 좋다.

하지만 제출 문서는 평가자가 빠르게 읽어야 하므로:

```text
검증된 완료 항목만 짧게 보여준다.
```

가 더 적합하다.

### 중요한 경계

- 미완료 필수 항목을 완료처럼 쓰면 안 된다.
- 그러나 제출에 불필요한 내부 불확실성을 모두 전시할 필요도 없다.

좋은 구조:

```text
internal evidence ledger
        ↓
검증
        ↓
submission surface
```

제출 문서의 주장은 evidence보다 강하면 안 된다.

---

## 22.4 “완료형 문서”를 만드는 마지막 순간이 오히려 위험하다

이번 실습에서는 최종 정리 과정에서:

- 실제 Git 이력
- SUBMISSION
- conflict 기록
- PR review 수

가 서로 다르게 해석되는 상황이 생겼다.

그래서 최종 제출 직전에는 새 내용을 추가하는 것보다 다음을 확인한다.

```text
SUBMISSION
↕
GitHub PR / Issue / Review
↕
Git history
↕
세부 evidence 문서
```

이 네 가지가 서로 모순되지 않는가?

이 과정을 **release gate**로 둔다.

# 23. 팀 협업에서 배운 운영 원칙

## 23.1 진행자는 모든 답을 대신하지 않는다

평가나 시연 자리에서 한 사람이 모든 것을 설명하면:

- 다른 팀원의 학습 증거가 사라진다.
- 팀원의 역할이 약해 보인다.
- 진행자 혼자만 과도하게 중심이 된다.

좋은 흐름:

```text
해당 작업 담당자가 먼저 설명
→ 필요하면 진행자가 짧게 보완
```

---

## 23.2 사람의 한 번의 표정·말투를 장기 평가로 고정하지 않는다

한 번 관찰된 행동은 다음처럼 기록하는 편이 낫다.

```text
“이 상황에서 이런 행동이 한 번 관찰됨”
```

보다 위험한 방식:

```text
“저 사람은 원래 이런 사람”
```

구체적인 반복 행동은 신뢰 판단에 사용할 수 있지만, 한 번의 긴장·실수·표정만으로 사람 전체를 고정 평가하지 않는다.

---

## 23.3 즉석 시연 능력도 학습 결과다

머리로 이해하지만 터미널에서 바로 입력하지 못하면 실전에서는 큰 차이가 난다.

자주 써서 손에 익힐 명령:

```bash
git status
git status --short
git branch --show-current
git log --oneline --graph --all
git diff
git diff --staged
git fetch origin
git switch <branch>
git stash
git stash list
git revert <sha>
```

목표는 타자 속도 자체가 아니라:

```text
문제 인식 → 적절한 명령 선택 → 실행 → 결과 설명
```

의 latency를 줄이는 것이다.

# 25. 실전에서 자주 틀리기 쉬운 것

### 1. commit과 push를 같은 것으로 생각하기

```text
commit = local
push   = remote로 전송
```

### 2. branch를 파일 사본이라고 생각하기

branch는 기본적으로 commit pointer다.

### 3. `origin/main`을 GitHub 실시간 상태라고 생각하기

`fetch`하지 않았다면 오래된 값일 수 있다.

### 4. merge conflict marker만 지우면 끝이라고 생각하기

의미를 결정하고 기능 검증까지 해야 한다.

### 5. reset과 revert를 “되돌리기”라는 한 단어로 묶기

history를 다루는 방식이 전혀 다르다.

### 6. amend는 같은 commit의 글자만 고친다고 생각하기

새 commit이 만들어져 SHA가 바뀐다.

### 7. `stash pop`이 언제나 안전하다고 생각하기

현재 변경과 겹치면 conflict가 날 수 있다.

### 8. Approve만 있으면 좋은 review라고 생각하기

구체적인 근거와 작성자의 반응이 있어야 협업 학습 가치가 커진다.

### 9. 에이전트가 만든 문서를 곧바로 사실로 생각하기

Git object, PR timeline, terminal result와 교차 검증한다.

# 28. 이해도 점수 기준

### 1점 — 보면 이해

명령어와 설명을 보면 “아는 내용”처럼 느껴진다.

### 2점 — 자료 없이 설명

왜 쓰는지 자신의 말로 설명할 수 있다.

### 3점 — 재구성

빈 저장소/터미널에서 직접 재현할 수 있다.

### 4점 — 변형·디버깅

조건이 바뀌어도 해결할 수 있다.

예:

- stash가 여러 개 있을 때 특정 항목 복원
- remote와 local branch가 어긋났을 때 상태 판단
- conflict가 문서가 아니라 코드에서 발생
- 이미 push한 잘못된 commit 안전하게 취소
- 리뷰 후 다른 파일까지 영향을 주는 regression 확인

목표는 명령어를 많이 외우는 것이 아니라 **3~4점 영역을 조금씩 늘리는 것**이다.

```text
주 5회 × 15분 = 주 75분
```

을 유지하는 것이다.

# 31. 이번 미션의 최종 압축

Git 협업을 다음 한 문장으로 기억한다.

> **변경을 분리하고, 이유를 기록하고, 다른 사람이 검증하고, 검증된 변경만 공유 기준선에 합친다.**

Git 명령어는 이 원칙을 구현하는 도구다.

```text
branch  → 변경 분리
commit  → 변경 기록
Issue   → 목적 기록
PR      → 변경 공개
Review  → 타인 검증
Merge   → 공유 기준선 반영
Revert  → 공유 이력을 보존하며 취소
Stash   → 미완성 변경 임시 보관
Ruleset → 협업 규칙을 시스템으로 강제
```

그리고 AI 에이전트를 추가하면 한 줄이 더 붙는다.

> **에이전트는 기록과 검증을 가속하지만, 실제 사람 행동과 최종 사실 판단을 대신하지 않는다.**
