# 코디세이 입학연수 통합 복습 — 실무 관점 (1년차 이상)

**대상:** 문법과 기본 명령은 이미 아는 사람. "무엇을 하는가"가 아니라 **"왜 그렇게 설계했고, 실무에서는 어디가 달라지는가"**가 필요한 사람
**전제:** 이 문서는 미션 요구사항을 다시 설명하지 않습니다. 요구사항이 **왜 그렇게 쓰였는지**, 그리고 그 요구사항의 **한계는 어디인지**를 다룹니다.
**주의:** 미션 명세를 그대로 따르는 것과 실무 기준을 따르는 것이 충돌하는 지점이 여러 곳 있습니다. 그 충돌을 숨기지 않고 표시했습니다. 제출물은 명세를 따르고, 발표에서는 차이를 아는 것으로 깊이를 보이는 게 맞습니다.

## 0부. 세 미션의 아키텍처적 위치

### 커리큘럼이 실제로 가르치려 한 것

| 미션 | 표면적 주제 | 실제 학습 목표 | 실무 대응 영역 |
|---|---|---|---|
| E1 | 터미널·Docker·Git | **실행 환경의 재현성** | 빌드/배포, 인프라 |
| E2 | Python·클래스·JSON | **상태의 수명 관리와 실패 격리** | 애플리케이션 설계 |
| E3 | MAC 연산·성능 측정 | **수치 신뢰성과 측정 방법론** | 성능 엔지니어링, 데이터 파이프라인 |

세 미션은 난이도 순이 아니라 **추상화 계층 순**으로 배치돼 있습니다. E1이 프로세스가 놓일 자리를, E2가 프로세스를, E3가 프로세스 안의 핫 루프를 다룹니다. 이 배치를 인지하고 발표하면 "미션을 순서대로 했다"가 아니라 "계층을 아래에서 위로 쌓았다"는 서술이 가능합니다.

### 세 미션에 반복 출현하는 설계 원리 여섯 개

이 표가 이 문서의 뼈대입니다. 나머지 절은 각 칸의 근거입니다.

| 원리 | E1 | E2 | E3 |
|---|---|---|---|
| **경계에서 정규화** | 환경 변수 우선순위(이미지 ENV → Compose → 런타임) | 화면 1-based ↔ 내부 인덱스 정규화 지점 단일화 | `'+'`/`'x'` → `Cross`/`X` 라벨 정규화 |
| **상태의 수명 계층 분리** | 이미지(불변) / 컨테이너(일회성) / 볼륨(영속) | 코드(불변) / 세션 상태(일회성) / `state.json`(영속) | 필터(입력, 불변) / 점수(계산 결과) / 리포트(영속) |
| **실패 격리 단위 선언** | 컨테이너 = 격리 경계 | `try/except`의 범위 = 복구 가능 단위 | 케이스 단위 FAIL, 배치는 계속 |
| **재현성 확보 수단** | 태그·다이제스트 고정 | 커밋 단위로 시점 고정 | 반복 측정 + 통계 요약 |
| **관측 가능성** | stdout 로그 규약, `docker logs` | 예외 메시지와 안내 문구 | PASS/FAIL 요약과 실패 사유 |
| **설정과 코드 분리** | `.env`, `templates/*.template` | 기본 데이터와 로직 분리 | 필터를 코드가 아닌 JSON에 배치 |

## 1부. E1 — 재현 가능한 실행 환경

### 1-1. 이미지 계층과 캐시 전략

Dockerfile의 각 명령은 계층(layer)을 하나씩 만들고, 빌더는 **계층 단위로 캐시**합니다. 어떤 계층의 입력이 바뀌면 그 이후 모든 계층이 무효화됩니다.

여기서 나오는 규칙은 하나입니다. **변경 빈도가 낮은 것을 위로, 높은 것을 아래로.**

```dockerfile
# 안티패턴 — 소스 한 줄만 고쳐도 의존성 설치가 다시 돔
COPY . .
RUN pip install -r requirements.txt

# 권장 — 의존성 목록이 안 바뀌면 설치 계층이 캐시에서 재사용됨
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

미션의 Dockerfile은 4줄뿐이라 이 효과가 드러나지 않지만, **왜 4줄로도 충분했는지**를 말할 수 있어야 합니다. 정적 파일만 다루므로 의존성 설치 계층이 없기 때문입니다.

**미션 Dockerfile에 없는 것들 — 실무라면 무엇이 추가되는가**

| 누락 항목 | 왜 필요한가 | 미션에서 없어도 됐던 이유 |
|---|---|---|
| `USER` (비루트 실행) | 컨테이너 탈출 시 피해 축소. 대부분의 보안 기준선이 요구 | nginx 공식 이미지가 워커를 비특권 사용자로 떨어뜨림. 다만 마스터는 root |
| `HEALTHCHECK` | 오케스트레이터가 "떴다"와 "받을 준비됐다"를 구분 | 단일 컨테이너 실습이라 판정 주체가 없음 |
| 멀티스테이지 빌드 | 빌드 도구를 최종 이미지에서 제외해 크기·공격면 축소 | 컴파일 단계가 없음 |
| 다이제스트 고정 (`@sha256:...`) | 태그는 재할당 가능. 다이제스트만이 진짜 불변 | 태그 고정만으로 과제 기준 충족 |
| `EXPOSE` | 포트 의도의 문서화. `-P` 자동 매핑의 근거 | 실제 매핑은 `-p`가 수행하므로 동작상 불필요 |

발표에서 쓸 문장: "이 Dockerfile은 최소 형태로 의도한 것이고, 실서비스라면 비루트 사용자·헬스체크·다이제스트 고정이 추가됩니다. 각각이 무엇을 막는지는 설명할 수 있습니다."

### 1-2. 태그, 다이제스트, 재현성의 실제 수준

| 지정 방식 | 재현성 | 실무 위치 |
|---|---|---|
| `nginx:latest` | 없음 | 금지 |
| `nginx:alpine` | 낮음 (alpine 판이 갱신되면 바뀜) | 학습·실험 |
| `nginx:1.27-alpine` | 중간 (패치 판은 갱신됨) | 대부분의 애플리케이션 |
| `nginx:1.27.3-alpine` | 높음 | 프로덕션 기본선 |
| `nginx@sha256:4a73...` | 완전 | 규제 환경, 공급망 보안 |

**흔한 오해:** "태그를 고정했으니 재현된다"는 부정확합니다. 태그는 **이름표라서 재할당될 수 있습니다.** 같은 태그가 어제와 오늘 다른 다이제스트를 가리킬 수 있습니다. 재현성을 진짜로 보장하는 건 다이제스트뿐입니다.

실무에서는 다이제스트를 직접 손으로 쓰지 않고, 락 파일이나 이미지 스캐너·갱신 봇이 관리합니다.

### 1-3. Alpine 선택의 트레이드오프

이미지 크기(약 60MB vs 약 190MB)만 보고 Alpine을 고르면 언어 런타임에서 대가를 치릅니다.

**핵심 원인:** Alpine은 glibc가 아닌 **musl libc**를 씁니다. PyPI의 바이너리 휠 상당수는 glibc 기준(`manylinux`)으로 빌드돼 Alpine에서 설치되지 않고, 소스 컴파일로 넘어갑니다. 그러면 빌드 시간이 수 분에서 수십 분으로 늘고, 컴파일 도구를 이미지에 넣어야 해서 크기 이점이 사라집니다.

`musllinux` 휠 표준이 생겨 상황이 나아지고 있지만 적용 범위는 패키지마다 다릅니다.

**판단 기준:**

| 상황 | 권장 |
|---|---|
| 정적 파일 서빙, Go 정적 바이너리 | Alpine |
| Python/Node 애플리케이션 | `-slim` 계열 (Debian 기반, 불필요 패키지 제거) |
| 과학 계산·컴파일 확장 다수 | 표준 Debian 기반 |

**추가로 알아둘 것:** musl의 스레드 기본 스택 크기가 glibc보다 작아서, 재귀가 깊거나 스택을 많이 쓰는 코드에서 Alpine에서만 세그폴트가 나는 사례가 있습니다. "Alpine에서만 죽는다"는 버그의 단골 원인입니다.

### 1-4. 비밀값 관리의 사다리

미션은 `.env`까지 다뤘습니다. 그 위가 어디까지 있는지 알아야 합니다.

| 단계 | 방식 | 노출 위험 | 적용 시점 |
|---|---|---|---|
| 0 | 코드에 하드코딩 | 저장소 전체에 영구 노출 | 절대 금지 |
| 1 | Dockerfile `ENV` | 이미지 받은 누구나 `docker history`로 조회 | 절대 금지 |
| 2 | `.env` + `.gitignore` | 서버 파일시스템에 평문 | 로컬 개발 |
| 3 | 오케스트레이터 시크릿 | 노드에 tmpfs 마운트, etcd 암호화 | 소규모 운영 |
| 4 | 외부 시크릿 관리자 | 중앙 관리, 감사 로그, 자동 회전 | 프로덕션 |

**`ARG`도 안전하지 않습니다.** 빌드 인자는 최종 이미지의 `ENV`에는 안 남지만 **빌드 히스토리에는 남습니다.** BuildKit의 시크릿 마운트(`--mount=type=secret`)를 써야 계층에 남지 않습니다.

**이미 커밋된 비밀값 대응 — 순서가 중요합니다.**
1. **먼저 해당 자격증명을 폐기·재발급합니다.** 이게 1순위입니다.
2. 그다음에 히스토리 정리를 검토합니다.

파일을 지우는 것은 해결이 아닙니다. Git은 과거 커밋에 객체를 보존하고, 이미 fork되거나 clone된 사본은 회수할 수 없습니다. **"유출된 값은 지워서 안전해지는 게 아니라 무효화해서 안전해집니다."**

**`.gitignore`의 알려진 함정:** 이미 추적 중인 파일에는 적용되지 않습니다. 추적에서만 빼려면 인덱스에서 제거해야 하는데, 이때 `--cached`를 붙이면 **디스크의 파일은 그대로 남습니다.**

```
git add .
```
```
git commit -m "chore: 추적 해제 전 현재 상태 저장"
```
커밋이 끝난 뒤에만 다음을 단독으로 실행합니다.
```
git rm --cached .env
```
- 하는 일: Git의 추적 목록에서만 제외합니다. `--cached`가 있으므로 **디스크의 `.env` 파일은 삭제되지 않습니다.**
- 정상일 때: `rm '.env'` 한 줄이 출력되고, `ls -la`로 확인하면 파일이 그대로 있습니다.
- 어긋났을 때: `--cached` 없이 실행하면 파일까지 사라집니다. 반드시 옵션을 확인하고 실행하세요.

### 1-5. 바인드 마운트 vs 볼륨 — 소유권 관점

교재는 보통 "개발용 / 운영용"으로 나누는데, 정확한 구분 기준은 **데이터의 소유자가 누구인가**입니다.

| | 바인드 마운트 | 명명 볼륨 |
|---|---|---|
| 데이터 소유 | 호스트 | Docker(드라이버) |
| 경로 결합도 | 호스트 경로에 강결합 | 이름으로만 참조 |
| 이식성 | 낮음 (다른 머신에서 경로 다름) | 높음 |
| 백업 | 호스트 도구로 | 볼륨 백업 절차 필요 |
| 권한 문제 | **자주 발생** (UID/GID 불일치) | 상대적으로 적음 |
| 원격 스토리지 | 불가 | 드라이버로 가능(NFS 등) |

**UID/GID 불일치 문제:** 호스트의 사용자 번호와 컨테이너 안 사용자 번호가 다르면, 마운트한 폴더의 파일이 컨테이너에서 남의 소유로 보이거나 쓰기가 거부됩니다. macOS는 파일 공유 계층이 이를 가려 주지만 **Linux 호스트에서는 그대로 드러납니다.** CI에서만 실패하는 마운트 버그의 흔한 원인입니다.

**`:ro`의 실제 가치:** 설정 파일·인증서처럼 읽기만 하면 되는 마운트는 읽기 전용으로 붙입니다. 컨테이너가 침해돼도 호스트 파일이 변조되지 않습니다. 최소 권한 원칙의 가장 값싼 적용입니다.

**미션이 증명하려 한 것의 정확한 서술:**
> "볼륨 영속성 실습은 '데이터가 남는다'가 아니라 **'컨테이너의 수명과 데이터의 수명을 분리했다'**를 증명한 것입니다. 컨테이너를 일회성으로 취급할 수 있게 되는 것이 목적이고, 무상태(stateless) 배포의 전제 조건입니다."

### 1-6. nginx 템플릿 치환 메커니즘

```nginx
listen ${NGINX_PORT};
```

이건 nginx 문법이 **아닙니다.** nginx는 이 표기를 이해하지 못합니다. 동작하는 이유는 공식 이미지의 엔트리포인트 스크립트 때문입니다.

`/docker-entrypoint.d/` 아래의 스크립트들이 컨테이너 시작 시 순서대로 실행되고, 그중 `20-envsubst-on-templates.sh`가 `/etc/nginx/templates/*.template`를 읽어 `envsubst`로 환경 변수를 치환한 뒤 `/etc/nginx/conf.d/`로 출력합니다. `.template` 확장자가 떨어지므로 `default.conf.template` → `default.conf`가 되어 기본 설정을 덮어씁니다.

**이 구조가 주는 것:** 이미지를 재빌드하지 않고 환경 변수만 바꿔 설정을 변경할 수 있습니다. 12-factor의 "설정을 환경에서 읽는다"를 이미지 수준에서 구현한 사례입니다.

**주의할 충돌:** nginx 자체 변수(`$host`, `$remote_addr`, `$uri`)와 치환 대상이 섞일 수 있습니다. `envsubst`는 실제로 존재하는 환경 변수만 치환하도록 스크립트가 목록을 넘기지만, 환경 변수 이름을 nginx 변수와 동일하게 지으면 설정이 깨집니다. 대문자 명명 관습이 이 사고를 막습니다.

**설정 변경 시 절차:** 반영 전에 문법 검사를 먼저 합니다.
```
nginx -t
```
- 하는 일: 설정 파일 문법만 검사하고 종료합니다. 서비스에 영향 없습니다.
- 정상일 때: `syntax is ok` / `test is successful` 두 줄
- 어긋났을 때: 잘못된 파일과 줄 번호를 알려줍니다. 컨테이너 안에서 실행하려면 `docker exec` 로 진입해 실행하세요.

문법 오류 상태로 시작하면 nginx가 기동을 거부하고, 재시작 정책에 따라 크래시 루프에 들어갑니다. 이때는 `docker logs`에 원인이 그대로 찍힙니다.

### 1-7. Compose에서 실무자가 짚어야 할 것

```yaml
services:
  web:
    build: .
    image: mission1-web-compose:1.0
    container_name: compose-web
    environment:
      NGINX_PORT: ${NGINX_PORT}
      APP_ENV: ${APP_ENV}
    ports:
      - "${HOST_PORT}:${NGINX_PORT}"
    volumes:
      - ./templates:/etc/nginx/templates:ro
  helper:
    image: alpine:latest
    container_name: compose-helper
    command: tail -f /dev/null
    depends_on:
      - web
```

**`version:` 키:** 현행 Compose 명세에서 폐기됐습니다. 남겨 두면 경고가 나옵니다. 인터넷 예제 대부분이 아직 갖고 있어 혼동을 유발합니다.

**포트 문자열의 따옴표:** YAML 1.1은 `22:22` 형태를 60진수 정수로 해석합니다. 두 값이 모두 60 미만일 때 실제로 발생하고, 결과적으로 의도와 다른 포트가 열립니다. 포트 항목은 항상 인용부호로 감싸는 것이 관습입니다.

**`container_name` 고정의 대가:** 이름은 유일해야 하므로 `--scale`로 복제할 수 없습니다. 수평 확장 대상 서비스에는 지정하지 않는 것이 맞습니다. 실습에서는 로그·명령 편의를 위해 고정한 것이고, **그 판단 근거를 말할 수 있으면 됩니다.**

**`depends_on`의 한계 — 가장 중요한 항목입니다.**

기본형은 **시작 순서만** 보장하고 준비 완료를 보장하지 않습니다. DB 컨테이너가 "시작"됐다고 접속을 받을 수 있는 건 아닙니다. "첫 부팅에서만 항상 실패한다"는 증상의 대부분이 여기서 나옵니다.

두 가지 대응이 있고, 실무는 후자를 더 신뢰합니다.

```yaml
# (1) 헬스체크 조건부 의존 — healthcheck 정의가 선행돼야 함
depends_on:
  db:
    condition: service_healthy
```

(2) **애플리케이션 측 재시도.** 서비스는 기동 시점뿐 아니라 운영 중에도 끊깁니다. 지수 백오프 재연결을 구현해 두면 기동 순서 문제와 운영 중 단절이 같은 코드로 해결됩니다. 오케스트레이션에 의존하는 것보다 견고합니다.

**암묵적 네트워크:** `networks:`를 쓰지 않으면 Compose가 프로젝트 기본 네트워크를 만들고 모든 서비스를 넣습니다. 서비스 이름이 곧 DNS 이름이 되어 `http://web:8080`이 동작합니다. **이건 내가 설정한 게 아니라 Compose의 기본 동작**이라는 점을 정확히 말할 수 있어야 합니다.

**`command: tail -f /dev/null` vs `sleep infinity`:** `sleep infinity`는 GNU coreutils의 확장 동작이고, Alpine의 BusyBox `sleep`은 `infinity` 인자를 받지 못하는 판이 있습니다. **같은 이름의 명령이 배포판마다 다른 구현일 수 있다**는 실무 함정의 좋은 사례이며, Alpine 사용 시 자주 만납니다.

### 1-8. 로그 규약

컨테이너 프로세스는 로그를 파일이 아니라 **stdout/stderr로 내보내는 것이 규약**입니다.

이유는 세 가지입니다. 첫째, 컨테이너가 사라지면 내부 파일도 사라집니다. 둘째, 로그 로테이션을 애플리케이션이 관리하면 관심사가 섞입니다. 셋째, 런타임이 로그를 수집해야 중앙 집계 파이프라인에 태울 수 있습니다.

nginx 공식 이미지는 `access.log`와 `error.log`를 `/dev/stdout`, `/dev/stderr`로 심볼릭 링크해 두었습니다. **`docker logs`로 다 보이는 이유가 이것**이고, 미션 로그를 설명할 때 짚으면 좋은 지점입니다.

**구조화 로그:** 규모가 커지면 평문 대신 JSON 라인 형식으로 내보냅니다. 파싱 없이 필드 검색이 가능해지기 때문입니다. 지금 단계에서 필요하진 않지만, 다음 계단으로 알아두면 됩니다.

### 1-9. OrbStack이 실제로 해결한 문제

캠퍼스에서 `sudo`가 제한돼 Docker Desktop 설치·데몬 제어가 막힌 상황이었습니다. 정확히 말하면 **컨테이너 실행에 관리자 권한이 본질적으로 필요한 것은 아닙니다.** Docker의 전통적 구조가 root 데몬에 의존했을 뿐입니다.

이 문제에 대한 업계의 답이 rootless 컨테이너 계열이고(Podman, rootless Docker 등), OrbStack은 macOS에서 경량 VM과 사용자 수준 데몬으로 같은 결과를 냅니다.

**설명할 때 정확한 표현:**
> "권한 제약을 우회한 게 아니라, 컨테이너 실행에 root가 필요하다는 전제 자체가 구현 세부사항이었습니다. 명령어 인터페이스가 동일했다는 게 그 증거입니다."

## 2부. E2 — 프로그램 구조와 상태 관리

### 2-1. 책임 분리의 판단 기준

미션은 "클래스 2개 이상"을 요구했지만, 개수는 결과이지 기준이 아닙니다. 기준은 **변경 이유가 같은 것끼리 묶는 것**입니다.

| 클래스 | 변경 이유 | 아는 것 | 모르는 것 |
|---|---|---|---|
| `Quiz` | 문제의 표현 방식이 바뀔 때 (힌트 추가, 선택지 개수 변경) | 자기 문제·선택지·정답 | 다른 문제, 사용자, 파일 |
| `QuizGame` | 게임 흐름이 바뀔 때 (메뉴 추가, 출제 정책 변경) | 문제 목록, 입출력, 저장소 | 개별 문제의 내부 표현 |

**`Quiz`가 `input()`이나 `print()`를 직접 호출하지 않는 것이 중요합니다.** 호출하는 순간 콘솔에 결합되어 테스트도, 웹 UI 이식도 불가능해집니다. `Quiz.check_answer(n) -> bool`은 순수 함수에 가깝고, 출력은 `QuizGame`이 담당합니다. **계산과 표현의 분리**이며, E3에서 "MAC 함수 안에서 print 하지 않는다"와 동일한 원리입니다.

**dataclass를 쓰지 않은 것에 대해:** `dataclasses`는 표준 라이브러리이므로 미션 제약(외부 라이브러리 금지)에 걸리지 않습니다. `@dataclass`로 쓰면 `__init__`·`__repr__`·`__eq__`가 자동 생성돼 보일러플레이트가 줄어듭니다. 다만 `__init__`과 `self`를 손으로 쓰는 것이 학습 목표였으므로 명시적 정의가 이 맥락에서는 타당합니다. **"알고 안 썼다"와 "몰라서 안 썼다"는 다르고, 발표에서는 전자로 말할 수 있어야 합니다.**

### 2-2. 직렬화 경계

`Quiz` 객체와 `state.json`의 dict는 **같은 것이 아닙니다.** 둘을 잇는 지점을 명시적으로 만들어야 합니다.

```python
class Quiz:
    def to_dict(self) -> dict:
        return {"question": self.question,
                "choices": self.choices,
                "answer": self.answer}

    @classmethod
    def from_dict(cls, d: dict) -> "Quiz":
        return cls(d["question"], d["choices"], d["answer"])
```

**왜 이 경계가 필요한가:** 저장 형식과 내부 표현이 결합되면 한쪽을 못 바꿉니다. 예를 들어 정답을 내부에서 0-based로 다루기로 결정해도, `from_dict`에서 한 번 변환하면 JSON 스키마는 1-based로 유지할 수 있습니다.

**이건 E3의 라벨 정규화와 정확히 같은 패턴입니다.** 외부 데이터의 표기 규칙을 내부 규칙으로 바꾸는 지점을 **한 곳에만** 두는 것. 도메인 주도 설계에서는 이 계층을 부패 방지 계층(anti-corruption layer)이라고 부릅니다.

**1-based / 0-based 문제:** 화면은 1번부터, 리스트는 0번부터입니다. 규칙은 하나입니다 — **변환 지점을 하나로 정하고 나머지 코드는 그 사실을 모르게 합니다.** 여기저기서 `-1`을 하면 오프바이원 버그가 반드시 납니다.

### 2-3. 저장의 원자성 — 미션 명세를 넘어서는 지점

미션은 `json.dump`만 요구하지만, 실무 기준으로는 부족합니다.

**문제:** `open(path, "w")`는 여는 즉시 기존 내용을 절단합니다. 쓰는 도중에 프로세스가 죽으면 **원본이 사라진 채 잘린 파일**이 남습니다. 최고 점수 갱신 직후 Ctrl+C가 들어오면 이 창이 실제로 열립니다.

```python
import json, os, tempfile

def save_state(path, data):
    directory = os.path.dirname(os.path.abspath(path))
    fd, tmp = tempfile.mkstemp(dir=directory, suffix=".tmp")
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as f:
            json.dump(data, f, ensure_ascii=False, indent=2)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp, path)      # 같은 파일시스템 안에서 원자적 교체
    except BaseException:
        if os.path.exists(tmp):
            os.replace(tmp, tmp + ".failed")   # 흔적을 남김
        raise
```

핵심 세 가지입니다.

1. **임시 파일을 같은 디렉터리에** 만듭니다. `os.replace`의 원자성은 동일 파일시스템 내에서만 보장됩니다.
2. **`flush` + `fsync`** 로 OS 버퍼를 디스크까지 내립니다. 이게 없으면 교체는 됐는데 내용이 안 내려간 상태에서 전원이 끊길 수 있습니다.
3. **`os.replace`** 는 POSIX·Windows 모두에서 원자적 교체를 제공합니다. 독자는 옛 파일 또는 새 파일 중 하나만 보게 되고, 중간 상태를 보지 않습니다.

미션 제출물에 이걸 넣을지는 선택입니다. 다만 **"왜 단순 `json.dump`가 위험한지"를 말할 수 있으면 이해도가 확실히 드러납니다.**

### 2-4. 손상 파일 처리 정책

미션 요구는 "손상되면 안내 후 기본 데이터로 복구"입니다. 실무 기준을 하나 더합니다 — **덮어쓰기 전에 손상본을 보존합니다.**

```python
import json, os, time

def load_state(path):
    try:
        with open(path, encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:
        return default_state()                      # 첫 실행: 정상 경로
    except (json.JSONDecodeError, UnicodeDecodeError) as e:
        backup = f"{path}.corrupt.{int(time.time())}"
        os.replace(path, backup)                    # 지우지 않고 이름만 바꿔 보존
        print(f"저장 파일이 손상되어 기본 데이터로 시작합니다. 원본은 {backup}에 보관했습니다. ({e})")
        return default_state()
```

**`FileNotFoundError`와 `JSONDecodeError`를 나눠 잡는 이유:** 전자는 **예상된 정상 경로**(첫 실행)이고 후자는 **이상 상황**입니다. 같은 블록에서 잡으면 로그에서 구분이 안 되고, 이상 상황이 조용히 묻힙니다.

**`except Exception`으로 뭉치지 않는 이유:** 예외의 종류가 곧 대응 방법입니다. 뭉치면 프로그래밍 오류(`TypeError`, `AttributeError`)까지 삼켜서, 버그가 "기본 데이터로 복구됨"이라는 정상 메시지 뒤에 숨습니다. 진단 불가능한 상태가 됩니다.

### 2-5. KeyboardInterrupt는 Exception이 아니다

1년차가 자주 놓치는 지점입니다.

```
BaseException
├── SystemExit
├── KeyboardInterrupt
├── GeneratorExit
└── Exception          ← 일반적인 오류는 전부 여기 아래
    ├── ValueError
    ├── OSError
    └── ...
```

**`except Exception:` 은 `KeyboardInterrupt`를 잡지 않습니다.** 이건 의도된 설계입니다 — 사용자의 중단 요청이 광범위한 예외 처리에 삼켜지면 안 되기 때문입니다.

미션이 요구한 "Ctrl+C에도 비정상 종료하지 않기"는 따라서 **최상위에서 명시적으로** 처리해야 합니다.

```python
def main():
    game = QuizGame()
    try:
        game.run()
    except (KeyboardInterrupt, EOFError):
        print("\n종료합니다.")
        game.save()            # 가능한 만큼 저장
    finally:
        pass
```

**`EOFError`를 같이 잡는 이유:** 입력 스트림이 닫히면(`Ctrl+D`, 파이프 종료) `input()`이 `EOFError`를 냅니다. 처리하지 않으면 무한 루프 안에서 예외가 계속 발생해 스택 트레이스가 폭주합니다. 자동화 테스트로 실행할 때 실제로 겪는 상황입니다.

### 2-6. 입력 검증의 단일 지점화

미션이 요구한 네 케이스(공백·빈 입력·파싱 실패·범위 밖)는 **함수 하나로 모아야** 합니다. 메뉴에서 한 번, 정답 입력에서 또 한 번 구현하면 두 곳의 동작이 갈라집니다.

```python
def read_int(prompt: str, low: int, high: int) -> int:
    while True:
        raw = input(prompt).strip()
        if not raw:
            print(f"입력이 비어 있습니다. {low}-{high} 사이의 숫자를 입력하세요.")
            continue
        try:
            value = int(raw)
        except ValueError:
            print(f"숫자가 아닙니다. {low}-{high} 사이의 숫자를 입력하세요.")
            continue
        if not (low <= value <= high):
            print(f"범위를 벗어났습니다. {low}-{high} 사이의 숫자를 입력하세요.")
            continue
        return value
```

**설계 포인트:**
- 유효한 값이 나올 때까지 **반환하지 않습니다.** 호출부가 검증을 신경 쓰지 않게 됩니다.
- 범위를 매개변수로 받아 메뉴(1-5)와 정답(1-4)에 재사용합니다.
- 안내 메시지가 실패 원인마다 다릅니다. 사용자가 무엇을 고쳐야 할지 알 수 있습니다.
- `int(raw)`는 `" 3 "`도 처리하지만, `strip()`을 명시해 두면 빈 입력 판정이 정확해집니다.

### 2-7. Git 워크플로 — 요구사항의 의도

| 요구사항 | 표면 | 실제 의도 |
|---|---|---|
| 커밋 10개 이상 | 개수 채우기 | **점진적 개발의 흔적**. 한 번에 다 만들지 않았다는 증거 |
| 기능 단위 커밋 | 메시지 형식 | 되돌리기(revert)와 이분 탐색(bisect)의 단위 |
| 브랜치 생성·병합 | 명령 사용 | 본줄기를 깨지 않고 작업하는 습관 |
| clone·pull 각 1회 | 명령 사용 | 원격이 진실의 원천이라는 감각 |

**`--no-ff`에 대한 균형 잡힌 서술:** 미션은 병합 흔적을 남기라고 하지만, 실무에는 반대 진영이 있습니다.

| 입장 | 근거 |
|---|---|
| `--no-ff` 지지 | 기능 단위가 병합 커밋으로 묶여 되돌리기가 쉽고, 브랜치 구조가 히스토리에 보존됨 |
| squash/rebase 지지 | 히스토리가 선형이라 읽기 쉽고, 작업 중 지저분한 커밋이 남지 않음 |

정답은 없고 팀 규약입니다. **어느 쪽이든 이유를 대면 됩니다.** "미션 요구라서 썼습니다"보다 "기능 경계를 히스토리에 남기려고 썼고, 선형 히스토리를 선호하는 팀은 squash를 씁니다"가 훨씬 낫습니다.

**`bisect`를 알아두면 커밋 단위의 가치가 체감됩니다.** 커밋 하나가 "한 가지 일"이면 이분 탐색으로 버그 도입 시점을 로그 시간에 찾을 수 있습니다. `add .`로 전부 뭉친 커밋은 이걸 불가능하게 만듭니다.

공용 iMac에서는 로컬과 원격이 갈라져 있을 수 있습니다. 작업 시작 전 확인 순서입니다.

- 하는 일: 작업 트리와 인덱스 상태, 현재 브랜치, 원격 대비 앞/뒤 커밋 수
- 정상: 브랜치명과 `working tree clean` 또는 변경 목록
- 어긋남: `not a git repository`면 저장소 밖. `detached HEAD`면 브랜치가 아닌 특정 커밋에 있음 — 이 상태에서 커밋하면 어느 브랜치에도 안 붙습니다

```
git log --oneline -5
```
- 하는 일: 최근 커밋 5개를 한 줄씩
- 정상: 기억하는 마지막 작업이 맨 위
- 어긋남: 모르는 커밋이 있으면 다른 사람 작업이거나 다른 시점입니다. `git fetch` 후 `git log --oneline origin/main -5`로 원격과 비교하세요

- 하는 일: 등록된 원격 주소 확인
- 정상: `origin`이 fetch/push 두 줄
- 어긋남: 비어 있으면 원격 미등록. 다른 사람 계정 주소면 푸시가 거부됩니다

## 3부. E3 — 수치 신뢰성과 측정 방법론

### 3-1. 부동소수점 — 정확한 이해

IEEE 754 배정밀도는 유효 숫자 약 15~17자리, 머신 엡실론은 약 2.22e-16입니다. 0.1이 2진 유한 소수로 표현되지 않는다는 것이 근본 원인입니다.

**미션의 epsilon 정책을 비판적으로 볼 것**

미션 권장값은 `abs(a - b) < 1e-9`이고, 이건 **절대 허용오차**입니다. 절대 허용오차는 **비교 대상의 크기에 의존**한다는 약점이 있습니다.

| 값의 크기 | 1e-9 절대 허용오차의 적절성 |
|---|---|
| 0~1 범위 (이 미션) | 적절 |
| 1e6 범위 | **지나치게 엄격** — 그 크기에서는 표현 간격 자체가 1e-10 수준 |
| 1e-12 범위 | **지나치게 관대** — 서로 다른 값이 전부 동점 처리됨 |

**누적 오차 추정:** 소박한 순차 합산의 오차 상한은 대략 `(n-1) × ε × Σ|xᵢ|` 입니다. 25×25=625항, 각 항이 최대 1이라면 대략 `624 × 2.22e-16 × 625 ≈ 8.7e-11`. 1e-9보다 한 자릿수 작으니 이 미션 데이터에서는 안전합니다. **하지만 여유가 10배뿐**이고, 값의 범위가 커지면 무너집니다.

**실무에서 쓰는 대안**

```python
import math

# 상대 + 절대 혼합. 0 근처에서도 안전
math.isclose(a, b, rel_tol=1e-9, abs_tol=1e-12)
```

`math.isclose`의 기본값은 `rel_tol=1e-9, abs_tol=0.0`입니다. `abs_tol`이 0이면 **0과 아주 작은 수의 비교가 실패**하므로, 0이 나올 수 있는 상황에서는 명시적으로 지정해야 합니다.

**합산 정확도를 높이는 방법**

```python
import math
score = math.fsum(products)   # 정확 반올림 합. 누적 오차 제거
```

`math.fsum`은 Shewchuk 알고리즘으로 정확히 반올림된 결과를 냅니다. Kahan 보정 합산도 같은 계열입니다. **다만 이 미션에서는 쓰지 않는 게 맞습니다** — MAC 루프를 직접 구현하는 것이 학습 목표이고, `fsum`은 성능 측정 대상도 왜곡합니다. **알고 안 썼다고 말할 수 있으면 됩니다.**

**정수 데이터에 대한 관찰:** 이 미션의 필터·패턴이 전부 0/1 정수라면 부동소수점 오차는 애초에 발생하지 않습니다. 오차가 나오는 건 `data.json`에 실수가 들어 있는 케이스뿐입니다. **"실수가 섞인 케이스에서만 이 정책이 작동한다"**고 정확히 서술하면 데이터를 실제로 확인했다는 신호가 됩니다.

### 3-2. UNDECIDED의 정책적 성격

동점을 UNDECIDED로 처리하면, expected가 `X`인 케이스는 **자동으로 FAIL**이 됩니다. 이건 버그가 아니라 **선택한 정책의 귀결**입니다.

가능한 정책이 최소 셋입니다.

| 정책 | 동작 | 적합한 상황 |
|---|---|---|
| 엄격 (미션 권장) | 동점 → UNDECIDED → FAIL | 오판정 비용이 높을 때. 모른다고 말하는 게 나은 경우 |
| 관대 | 동점 → 사전 정의된 기본 라벨 | 반드시 답을 내야 하는 파이프라인 |
| 유보 후 위임 | 동점 → 별도 큐로 보내 재판정 | 사람 검토가 가능한 실무 시스템 |

README에 쓸 문장:
> "동점을 UNDECIDED로 처리하고 이를 FAIL로 집계하는 정책을 선택했습니다. 이는 오판정보다 판정 유보가 낫다는 판단이며, 반대로 항상 라벨이 필요한 시스템이라면 기본 라벨로 떨어뜨리는 정책이 맞습니다."

**이 서술 하나가 "실패를 못 고쳤다"를 "정책을 선택했다"로 바꿉니다.**

### 3-3. 스키마 검증과 실패 격리

미션은 "크기 불일치 시 프로그램이 중단되면 안 되고 케이스 단위 FAIL"을 요구합니다. 이건 **fail-fast의 반대 선택**이고, 그 이유가 있습니다.

| 전략 | 언제 맞나 |
|---|---|
| Fail-fast (즉시 중단) | 설정 로딩, 부팅 시 검증. 잘못된 상태로 진행하는 게 더 위험할 때 |
| 케이스 단위 저하 (미션 선택) | 배치 처리. 한 건의 불량이 전체 배치를 막으면 안 될 때 |

**배치 처리에서 케이스 단위 저하를 택하는 이유:** 1000건 중 3건이 불량일 때 전체를 중단하면 997건의 정상 처리를 잃습니다. 대신 **실패 건을 식별자와 사유와 함께 기록**해서 나중에 재처리합니다. 미션의 "실패 케이스 목록 출력" 요구가 정확히 이 재처리 가능성을 위한 것입니다.

**구현 형태:**

```python
def evaluate_case(case_id, pattern, filters, epsilon):
    """판정 결과를 '반환'한다. 출력하지 않는다."""
    n = len(pattern)
    if any(len(row) != n for row in pattern):
        return Result(case_id, status="FAIL", reason="패턴이 정방행렬이 아님")
    if n not in filters:
        return Result(case_id, status="FAIL", reason=f"size_{n} 필터 없음")
    # ... MAC 계산 및 판정
```

**계산 함수 안에서 `print`하지 않는 것**이 핵심입니다. 반환값으로 넘기면 콘솔 출력, 파일 기록, 테스트 어서션에 모두 재사용됩니다. E2에서 `Quiz`가 출력을 하지 않는 것과 같은 원리입니다.

### 3-4. 측정 방법론 — 미션 기준을 넘어서는 부분

미션 요구는 "10회 반복 평균"입니다. 성능 측정 관점에서 개선 여지가 큽니다.

**(1) 타이머 선택**

| 함수 | 특성 |
|---|---|
| `time.time()` | 벽시계. NTP 보정으로 **뒤로 갈 수 있음**. 구간 측정에 부적합 |
| `time.perf_counter()` | 단조 증가, 최고 해상도. **구간 측정의 표준** |
| `time.process_time()` | CPU 시간만. 대기 시간 제외 |

**(2) 평균보다 최소/중앙값**

측정 잡음은 **한쪽 방향**입니다. OS 스케줄링, 다른 프로세스, 캐시 축출은 시간을 늘리기만 합니다. 따라서 평균은 잡음에 오염되고, **최소값이 "방해 없는 실행"에 가장 가깝습니다.** `timeit` 문서도 최소값 사용을 권합니다.

실무 절충: **중앙값**을 대표값으로, **최소·최대**를 함께 보고합니다. 미션 제출은 요구대로 평균을 넣되, 중앙값을 함께 적으면 방법론을 아는 것으로 읽힙니다.

**(3) 워밍업**

첫 호출은 함수 객체 조회, 로컬 캐시 준비 등으로 느립니다. **첫 1~2회를 버리고** 측정하는 것이 표준입니다.

**(4) 가비지 컬렉션**

`timeit.Timer`는 측정 중 GC를 기본으로 비활성화합니다. 수동 측정 시 `gc.disable()`을 검토할 수 있으나, GC 부담 자체가 관심사라면 켜 둡니다. **무엇을 재려는지에 따라 결정합니다.**

**(5) 반복 횟수 자체가 부족한 경우**

3×3 MAC은 9회 곱셈입니다. `perf_counter`의 해상도와 함수 호출 오버헤드가 계산 시간보다 클 수 있습니다. 이 경우 **한 번의 측정 안에서 여러 번 반복**해 총 시간을 나눠야 유의미합니다.

```python
import time

def measure(fn, args, inner=1000, outer=10, warmup=2):
    for _ in range(warmup):
        fn(*args)
    samples = []
    for _ in range(outer):
        t0 = time.perf_counter()
        for _ in range(inner):
            fn(*args)
        t1 = time.perf_counter()
        samples.append((t1 - t0) / inner)
    samples.sort()
    return {
        "min_ms":    samples[0] * 1000,
        "median_ms": samples[len(samples) // 2] * 1000,
        "mean_ms":   sum(samples) / len(samples) * 1000,
    }
```

**README에 쓸 한 줄:** "3×3은 연산 시간이 타이머 해상도에 근접해 내부 반복으로 증폭 측정했습니다. 그렇지 않으면 함수 호출 오버헤드가 측정값을 지배합니다."

### 3-5. O(N²) 주장의 검증

"N²이니까 O(N²)"는 이론적 근거이고, 실측으로 뒷받침해야 완결됩니다.

**검증 방법:** 시간과 크기를 로그-로그 축에 놓으면 기울기가 지수가 됩니다.

```
log(T) = k·log(N) + c   →  k ≈ 2 이면 O(N²)
```

3×3 → 25×25는 한 변이 8.33배, 연산 횟수는 69.4배입니다. 측정 시간의 비가 69배 부근이면 주장이 지지됩니다.

**어긋날 때의 해석이 더 중요합니다.**

| 관측 | 가능한 원인 |
|---|---|
| 작은 N에서 시간이 예상보다 큼 | 함수 호출·루프 셋업 오버헤드가 지배. **상수항이 큰 것** |
| 큰 N에서 예상보다 급격히 증가 | 캐시 미스 증가, 리스트 재할당 |
| 비율이 69배가 아니라 40배 정도 | 작은 N의 측정이 오버헤드로 부풀려진 상태 |

**"이론값과 실측이 어긋난 이유를 설명한 README"가 "일치했다는 README"보다 높게 평가됩니다.** 어긋남을 설명할 수 있다는 게 이해의 증거이기 때문입니다.

**용어 정확성:** 이 미션은 **단일 위치 겹침**이므로 O(N²)입니다. 실제 합성곱은 K×K 필터를 N×N 입력 위로 미끄러뜨리므로 O(N²K²)이고, 채널과 필터 개수까지 곱해집니다. **미션이 다룬 것이 합성곱 전체가 아니라 그 최소 단위라는 점**을 정확히 말하면 좋습니다.

### 3-6. 1차원 평탄화 최적화 — 기대와 현실

보너스 과제인 2차원 → 1차원 변환의 효과를 정확히 이해할 필요가 있습니다.

**교과서적 근거(C 등):** 2차원 배열을 1차원 연속 메모리로 만들면 캐시 지역성이 좋아져 크게 빨라집니다.

**CPython에서의 현실은 다릅니다.**

파이썬 `list`는 값이 아니라 **PyObject 포인터의 배열**입니다. `[[1,2],[3,4]]`를 평탄화해 `[1,2,3,4]`로 만들어도, 리스트가 담는 건 여전히 정수 객체를 가리키는 포인터입니다. 실제 값은 힙 여기저기에 흩어져 있습니다. **즉 연속 메모리 접근이라는 이점 자체가 거의 없습니다.**

그럼에도 측정상 빨라지는 경우가 있는데, 원인은 다릅니다.

1. `grid[i][j]`는 `__getitem__` 두 번, `flat[i*n+j]`는 한 번입니다. **인터프리터 바이트코드 실행 횟수가 줄어듭니다.**
2. 내부 리스트 객체 조회가 사라집니다.

**정확한 서술:**
> "평탄화의 이득은 캐시 지역성이 아니라 인터프리터 오버헤드 감소에서 나옵니다. CPython 리스트는 포인터 배열이라 값이 연속 배치되지 않기 때문입니다. 진짜 지역성 이득은 `array` 모듈이나 NumPy처럼 값을 연속 저장하는 자료구조에서 나옵니다."

이 서술이 가능하면 보너스 과제를 "해봤다"가 아니라 "측정하고 원인을 규명했다"로 만들 수 있습니다.

### 3-7. 왜 NumPy가 빠르고, 왜 NPU가 필요한가

미션은 NumPy를 금지했습니다. **금지된 것의 정체를 아는 것이 이 미션의 진짜 목표입니다.**

**NumPy가 빠른 이유 세 가지**

1. **연속 메모리에 원시 값 저장.** 포인터 간접 참조가 없어 캐시 라인 하나에 여러 값이 들어옵니다.
2. **루프가 C에 있음.** 파이썬 루프는 반복마다 바이트코드 디스패치가 발생합니다. 그 오버헤드가 사라집니다.
3. **SIMD 벡터화.** 한 명령으로 4~8개 원소를 동시 처리합니다. BLAS 연동 시 캐시 블로킹까지 적용됩니다.

**NPU가 별도로 필요한 이유**

CPU에 SIMD가 있는데도 전용 칩이 필요한 건 **산술 강도(arithmetic intensity)** 때문입니다. MAC은 데이터당 연산량이 낮아 **메모리 대역폭에 병목**이 걸립니다.

| 접근 | 핵심 아이디어 |
|---|---|
| CPU SIMD | 소수의 강력한 코어. 분기 예측·비순차 실행에 트랜지스터 투자 |
| GPU | 다수의 단순 코어. 처리량 지향 |
| NPU/TPU 시스톨릭 어레이 | MAC 유닛을 격자로 배열하고 **데이터를 유닛 사이로 흘려보냄**. 한 번 읽은 값을 여러 연산에 재사용해 메모리 왕복을 최소화 |

여기에 **양자화**(FP32 → INT8)가 더해집니다. 정밀도를 낮추면 메모리 대역폭이 4분의 1이 되고 MAC 유닛을 더 촘촘히 넣을 수 있습니다. 추론에서는 정확도 손실이 대체로 허용 범위입니다.

**E3와의 연결 — 발표용 마무리:**
> "미션에서 epsilon 정책을 만든 이유가 여기서 다시 나옵니다. AI 하드웨어는 속도를 위해 정밀도를 의도적으로 낮춥니다. **수치 오차를 다루는 정책이 없으면 그 트레이드오프를 쓸 수 없습니다.** 부동소수점 비교를 손으로 구현한 것이 그 감각의 출발점입니다."

|---|---|---|---|
| E1 인프라 | 컨테이너 | 볼륨 | 마운트 지점 |
| E2 애플리케이션 | 세션 변수 | `state.json` | `to_dict`/`from_dict` |
| E3 계산 | 중간 점수 | 리포트 | 결과 객체 |

**문제: "외부 표기를 내부 표기로 어디서 바꾸는가?"**

| 계층 | 외부 | 내부 | 변환 지점 |
|---|---|---|---|
| E1 | `.env` 문자열 | 컨테이너 환경 변수 | Compose 치환, envsubst |
| E2 | JSON dict, 1-based 화면 번호 | `Quiz` 객체, 0-based 인덱스 | `from_dict`, 입력 검증 함수 |
| E3 | `'+'`, `'x'`, `'cross'` | `Cross`, `X` | 정규화 함수 |

**세 번 반복된 원리:** 변환은 **경계에서 한 번**, 내부는 표준 표기만. 이걸 어기면 표기 종류가 늘 때 수정 지점이 코드 전체로 퍼집니다.

**문제: "실패했을 때 어디까지 무너지는가?"**

| 계층 | 격리 단위 | 실패 시 |
|---|---|---|
| E1 | 컨테이너 | 하나가 죽어도 다른 컨테이너는 유지. 재시작 정책으로 복구 |
| E2 | `try/except` 블록 범위 | 파일 손상 → 기본값 복구, 프로세스는 유지 |
| E3 | 케이스 | 한 건 FAIL, 배치는 계속. 사유 기록 후 재처리 가능 |

### 4-2. 발표 서사 구성

세 미션을 30분에 넣을 때, 시간순 나열보다 **원리축 서술**이 강합니다.

| 구간 | 내용 |
|---|---|
| 도입 3분 | "세 미션은 계층이 다를 뿐 같은 질문에 답합니다 — 상태를 어디에 두고, 실패를 어디서 막고, 무엇을 재현 가능하게 만들 것인가" |
| 축 1 (7분) | **상태의 수명** — 볼륨 영속성 증명 화면 → `state.json` 원자적 저장 → 계산 결과의 반환 |
| 축 2 (7분) | **경계에서의 정규화** — 환경 변수 우선순위 → `from_dict` → 라벨 정규화. 셋이 같은 패턴임을 보임 |
| 축 3 (7분) | **실패 격리와 관측** — 컨테이너 재시작 → 예외 분류 처리 → 케이스 단위 FAIL과 리포트 |
| 마무리 6분 | **측정과 판단** — O(N²) 실측 대비, epsilon 정책 선택, 알고도 안 쓴 것들(`fsum`, dataclass, `--scale`) |

**마무리에서 "알고도 안 썼다"를 명시하는 것이 이 구성의 핵심입니다.** 제약 조건 안에서 의도적으로 선택했다는 서술은, 단순히 요구사항을 충족한 서술과 전혀 다른 신호를 줍니다.

## 5부. 코드 리뷰 체크리스트

제출 전, 그리고 앞으로의 작업에서 그대로 쓸 수 있는 항목입니다.

### 5-1. 컨테이너

- [ ] 베이스 이미지 태그가 고정되어 있는가 (`latest` 아님)
- [ ] 비밀값이 `ENV`·`ARG`·이미지 계층에 없는가
- [ ] `.dockerignore`에 `.git`, `.env`, 대용량 산출물이 들어 있는가
- [ ] 변경 빈도가 높은 `COPY`가 뒤쪽에 있는가
- [ ] 읽기 전용으로 충분한 마운트에 `:ro`가 붙어 있는가
- [ ] 포트 바인딩이 필요 이상으로 열려 있지 않은가 (로컬 확인용이면 `127.0.0.1:` 접두)
- [ ] 로그가 stdout/stderr로 나가는가
- [ ] `depends_on`이 준비 완료를 보장한다고 오해하고 있지 않은가

### 5-2. 애플리케이션

- [ ] 도메인 객체가 입출력을 직접 호출하지 않는가
- [ ] 직렬화 경계(`to_dict`/`from_dict`)가 명시적인가
- [ ] 예외를 종류별로 잡는가 (`except Exception` 뭉치기 없음)
- [ ] `KeyboardInterrupt`/`EOFError`가 `Exception` 밖이라는 걸 반영했는가
- [ ] 파일 저장이 부분 쓰기에 안전한가 (임시 파일 + 원자적 교체)
- [ ] 손상 데이터를 덮어쓰기 전에 보존하는가
- [ ] 입력 검증이 한 곳에 모여 있는가
- [ ] 1-based/0-based 변환 지점이 하나인가

### 5-3. 수치·성능

- [ ] 부동소수점을 `==`로 비교하지 않는가
- [ ] 차이 비교에 `abs`가 있는가
- [ ] 허용오차가 절대인지 상대인지 의식하고 선택했는가
- [ ] 동점 처리 정책이 문서화되어 있는가
- [ ] 측정에 `perf_counter`를 쓰는가
- [ ] 워밍업을 버리는가
- [ ] 측정 구간에서 I/O가 배제됐는가
- [ ] 측정 단위가 타이머 해상도보다 충분히 큰가
- [ ] 복잡도 주장이 실측으로 뒷받침되는가
- [ ] `[[0]*n]*n` 같은 얕은 복제가 없는가

## 6부. 심화 질의응답

동료평가에서 깊게 파고들 때 대비.

| 질문 | 답의 뼈대 |
|---|---|
| 태그를 고정했는데도 재현이 안 될 수 있나? | 예. 태그는 재할당 가능한 이름표입니다. 완전한 고정은 다이제스트뿐입니다. |
| `ENV`와 `ARG` 중 비밀값에 더 안전한 쪽은? | 둘 다 부적합합니다. `ARG`는 최종 이미지 `ENV`엔 안 남지만 빌드 히스토리에 남습니다. BuildKit 시크릿 마운트가 답입니다. |
| Alpine이 항상 좋은 선택인가? | 아니오. musl 기반이라 glibc용 바이너리 휠이 안 맞아 소스 빌드로 넘어갑니다. 정적 서빙엔 적합, 언어 런타임엔 `-slim`이 무난합니다. |
| `depends_on`으로 DB 준비를 보장할 수 있나? | 아니오. 시작 순서만 보장합니다. 헬스체크 조건부 의존이나 애플리케이션 재시도가 필요하며, 실무는 후자를 더 신뢰합니다. |
| 왜 로그를 파일이 아니라 표준 출력으로? | 컨테이너 소멸 시 파일도 사라지고, 런타임이 수집해야 중앙 집계가 가능하며, 로테이션 관심사를 애플리케이션에서 분리하기 위해서입니다. |
| `json.dump`만으로 저장하면 뭐가 위험한가? | `"w"`가 여는 즉시 절단하므로, 쓰는 도중 중단되면 원본 없이 잘린 파일만 남습니다. 임시 파일 + `os.replace`로 원자적 교체해야 합니다. |
| `except Exception`으로 다 잡으면 안 되는 이유는? | 예외 종류가 대응 방법이기 때문입니다. 뭉치면 프로그래밍 오류까지 삼켜 정상 메시지 뒤에 버그가 숨습니다. `KeyboardInterrupt`는 `Exception` 밖이라 잡히지도 않습니다. |
| 왜 `Quiz`가 `print`를 안 하나? | 콘솔에 결합되면 테스트와 다른 UI 이식이 막힙니다. 계산은 반환하고 표현은 상위가 담당합니다. E3의 계산 함수와 같은 원칙입니다. |
| epsilon 1e-9는 항상 적절한가? | 아니오. 절대 허용오차라 값의 크기에 의존합니다. 0~1 범위에선 적절하지만 큰 값에선 과도하게 엄격합니다. `math.isclose`의 상대+절대 혼합이 일반적입니다. |
| 이 데이터에서 부동소수점 오차가 실제로 나나? | 0/1 정수만이면 나지 않습니다. 실수가 섞인 케이스에서만 정책이 작동합니다. |
| UNDECIDED로 FAIL이 났는데 왜 안 고쳤나? | 고칠 버그가 아니라 선택한 정책입니다. 오판정보다 유보가 낫다는 판단이며, 항상 라벨이 필요한 시스템이라면 기본 라벨로 떨어뜨립니다. |
| 평균 대신 무엇을 봐야 하나? | 최소 또는 중앙값입니다. 측정 잡음은 시간을 늘리는 방향으로만 작용하므로 평균은 오염됩니다. |
| 1차원 평탄화가 왜 빨라지나? | 캐시 지역성이 아니라 인터프리터 오버헤드 감소 때문입니다. CPython 리스트는 포인터 배열이라 값이 연속 배치되지 않습니다. |
| NumPy 없이 구현한 게 무슨 의미인가? | 금지된 것의 정체를 알기 위해서입니다. NumPy의 이득은 연속 메모리·C 루프·SIMD 셋이고, NPU는 거기에 데이터 재사용과 양자화를 더한 것입니다. |
| 이 미션의 O(N²)와 실제 합성곱의 복잡도는? | 미션은 단일 겹침이라 O(N²)입니다. 슬라이딩 합성곱은 O(N²K²)이고 채널·필터 수가 더 곱해집니다. |

## 7부. 다음 계단

세 미션의 산출물을 실제 제품 쪽으로 잇는 순서입니다. 각 칸이 앞 칸을 전제합니다.

| 단계 | 내용 | 재사용되는 것 |
|---|---|---|
| 1 | 컨테이너의 정적 페이지 자리에 파이썬 웹 서버 배치 | E1 Dockerfile, 포트 매핑 |
| 2 | 그 서버가 외부 API를 호출 — 자격증명은 환경 변수로 | E1 `.env` 구조, E2 예외 처리 |
| 3 | DB 컨테이너 추가, Compose로 결합, 헬스체크 부착 | E1 Compose, 볼륨 |
| 4 | 상태 저장을 파일에서 DB로 이관 | E2 직렬화 경계 (여기서 값을 함) |
| 5 | 테스트 추가 — 계산 함수부터 | E2·E3의 "출력 안 하는 함수" 설계 |
| 6 | CI에서 빌드·테스트·이미지 푸시 자동화 | E1 저장소, 태그 전략 |
| 7 | 클라우드 배포 | 전부 |

**4단계에서 직렬화 경계의 가치가 드러납니다.** `to_dict`/`from_dict`가 있으면 저장소 교체가 그 두 함수와 저장소 어댑터에 국한됩니다. 없으면 `Quiz`의 내부 표현이 JSON 형식과 얽혀 있어 전면 수정이 됩니다. **지금 그 경계를 만들어 둔 것이 나중에 값을 하는 구조입니다.**

**5단계가 이 과정에서 가장 저평가된 항목입니다.** E2의 `Quiz.check_answer`와 E3의 MAC 함수는 이미 순수 함수에 가까워 테스트하기 쉬운 상태입니다. 테스트를 붙이는 순간 "돌아간다"가 "돌아간다는 것을 증명했다"로 바뀌고, 동료평가에서 설명 근거로도 쓸 수 있습니다.

## 부록. 이 문서의 한계

**첫째, 미션 명세와 실무 기준이 충돌하는 지점을 표시했지만 제출물은 명세를 따라야 합니다.** 원자적 저장이나 `math.fsum`을 넣어 명세의 학습 의도(직접 구현)를 훼손하면 오히려 감점 요인입니다. 아는 것과 쓰는 것을 구분하세요.

**둘째, 성능 수치는 환경 의존적입니다.** 여기 적은 이미지 크기, 오차 상한, 배수는 특정 환경 기준의 근사입니다. 발표에서는 반드시 **본인 측정값**을 쓰고, 이 문서의 숫자는 해석의 틀로만 쓰세요.

**셋째, 반대 관점.** 이 문서는 "설계 근거를 말할 수 있게 되자"는 방향입니다. 여기엔 반론이 있습니다 — 시제품 단계에서 이 수준의 정합성 투자는 과잉이고, 빠르게 만들어 빠르게 폐기하는 쪽이 낫다는 견해입니다. 이 반론은 **검증 전 단계에서는 대체로 옳습니다.** 다만 동료평가라는 구체적 상황에서는 설명 능력 자체가 평가 대상이므로 적용되지 않고, 코드가 살아남기 시작하는 순간부터는 반대로 이 문서의 항목들이 비용을 결정합니다. 어느 국면에 있는지 판단해서 쓰세요.
