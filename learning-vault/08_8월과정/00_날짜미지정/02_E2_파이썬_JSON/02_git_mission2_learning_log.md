> 원문에 있던 채팅 UI 문구, 시간 표시, 중복 명령 설명은 제거했습니다.

## 1. 오늘 학습한 핵심 개념

### Python과 프로그램 구조

1. 컴퓨터 프로그램은 입력받은 값을 정해진 규칙에 따라 처리하고 결과를 출력합니다.
2. 변수는 값을 가리키기 위해 사람이 붙인 이름입니다.
3. Python은 일반적으로 파일의 최상위 코드를 위에서 아래로 실행합니다.
4. 작은 프로그램은 먼저 `입력 → 처리 → 출력`로 이해하면 됩니다.
5. `for`는 준비된 대상이나 정해진 횟수를 순서대로 처리할 때, `while`은 종료 시점을 미리 확정하기 어려울 때 적합합니다.
6. 함수는 여러 줄의 명령에 이름을 붙인 묶음입니다.
7. `def greet(name):`에서 `def`는 함수 정의, `greet`는 함수 이름, `name`은 외부에서 받을 매개변수입니다.
8. 함수는 중복을 줄이고 역할을 분리하며 수정과 테스트 범위를 좁힙니다.
9. 관련된 데이터와 함수가 늘어나면 클래스로 함께 묶을 수 있습니다.
10. 클래스는 설계도, 객체는 프로그램 안에 실제로 만들어진 값입니다.
11. 인스턴스는 그 객체가 특정 클래스로부터 만들어졌다는 관계를 강조합니다.
12. 클래스 안에 정의된 함수는 메서드라고 부릅니다.
13. `__init__`은 흔히 초기화 메서드라고 부르며 새 인스턴스의 초기 속성을 설정합니다.
14. `self`는 현재 메서드를 실행 중인 객체를 가리킵니다.
15. 실행 중인 변수와 객체의 상태는 기본적으로 메모리에 있으며, 프로그램 종료 후 유지하려면 파일에 기록해야 합니다.
16. JSON은 문자열, 숫자, 참·거짓, 배열, 객체, `null` 같은 제한된 자료형을 표현합니다.
17. `Quiz` 객체는 저장 전에 딕셔너리로 바꾸고, 불러온 딕셔너리는 다시 `Quiz` 객체로 복원합니다.
18. `int("abc")`는 `ValueError`를 일으킵니다. 예상한 예외를 처리하면 안내 후 다시 입력받는 흐름을 만들 수 있습니다.
19. 직렬화는 프로그램의 데이터를 저장·전송 가능한 표현으로 바꾸는 과정이며, 역직렬화는 그 표현을 다시 프로그램의 자료형으로 읽는 과정입니다.
20. 클래스는 사용자가 정의하는 새로운 자료형의 정의라고 이해할 수 있습니다.

자세한 설명은 `10_CONCEPTS/01_python_quiz_game_core.md`를 기준 문서로 사용합니다.

## 2. Git의 기본 모델

```text
작업 폴더
   │ git add
   ▼
스테이징 영역
   │ git commit
   ▼
로컬 Git 저장소
   │ git push
   ▼
GitHub 원격 저장소
```

반대 방향은 다음과 같습니다.

```text
GitHub 원격 저장소
   │ git pull
   ▼
로컬 저장소와 작업 폴더
```

핵심은 다음 네 문장으로 압축할 수 있습니다.

- `add`: 다음 커밋에 포함할 변경을 선택
- `commit`: 선택한 변경을 로컬 이력으로 확정
- `push`: 로컬 커밋을 GitHub에 업로드
- `pull`: 원격의 새 커밋을 내려받아 현재 브랜치에 통합

`commit`만 해서는 GitHub에 올라가지 않습니다.

## 3. 상태 확인과 기본 설정

### 설치 확인

```bash
git --version
```

Git이 설치되어 있는지와 버전을 확인합니다.

### 현재 상태 확인

```bash
git status
```

현재 브랜치, 수정된 파일, 스테이징된 파일, 원격과의 차이를 확인합니다. 파일을 변경하지 않는 안전한 명령이므로 작업 전후 가장 먼저 사용합니다.

### 브랜치 확인

```bash
git branch
```

로컬 브랜치 목록을 보여 주며 현재 브랜치 앞에 `*`가 표시됩니다.

### 원격 주소 확인

```bash
git remote -v
```

원격 저장소의 가져오기와 보내기 주소를 확인합니다.

### 현재 저장소의 작성자 정보 확인

```bash
git config user.name
git config user.email
```

### 현재 저장소에만 작성자 정보 설정

```bash
git config user.name "본인이름"
git config user.email "GitHub에 등록한 이메일"
```

`--global`을 붙이지 않으면 현재 저장소에만 적용됩니다. 공용 컴퓨터에서는 다른 사용자의 설정을 바꾸지 않기 위해 로컬 설정을 우선합니다.

### 인증 정보 자동 저장 끄기

```bash
git config --local credential.helper ""
```

현재 저장소에서는 상위 설정에 등록된 credential helper 목록을 비워 인증 정보가 자동 저장되는 것을 막는 용도로 사용할 수 있습니다. 공용 컴퓨터에서는 별도의 보안 절차가 필요하며, 자세한 흐름은 루트 `README.md`를 따릅니다.

## 4. 저장소 만들기와 원격 연결

### 현재 폴더를 Git 저장소로 만들기

```bash
git init
```

현재 폴더에 숨김 관리 디렉터리 `.git`을 만듭니다. 이미 Git 저장소인 폴더에서는 반복 실행할 필요가 없습니다.

### 기본 브랜치 이름을 `main`으로 통일

```bash
git branch -M main
```

- `branch`: 브랜치 관리
- `-M`: 현재 브랜치 이름을 강제로 변경
- `main`: 새 이름

### 원격 저장소 최초 등록

```bash
git remote add origin https://github.com/내아이디/저장소이름.git
```

`origin`은 원격 저장소에 붙이는 관례적인 별명입니다.

### 잘못된 원격 주소 수정

```bash
git remote set-url origin 올바른주소
```

이미 `origin`이 있을 때 `remote add`를 다시 실행하지 않고 주소를 수정합니다.

## 5. 변경 기록 만들기

### 변경 선택

```bash
git add .
```

현재 폴더와 하위 폴더의 변경을 다음 커밋 후보로 올립니다. 초보 단계에서는 의도하지 않은 파일이 들어가는 것을 막기 위해 먼저 `git status`를 보고, 가능하면 파일명을 직접 지정하는 편이 안전합니다.

```bash
git add game.py quiz.py
```

### 커밋

```bash
git commit -m "Feat: 퀴즈 추가 기능 구현"
```

스테이징된 변경을 하나의 로컬 기록으로 확정합니다.

- `-m`: 커밋 메시지를 명령줄에서 지정
- 메시지: 무엇을 왜 바꿨는지 드러내는 한 문장

`git add`하지 않은 변경은 일반적으로 해당 커밋에 포함되지 않습니다.

### 원격으로 보내기

최초 연결:

```bash
git push -u origin main
```

- `-u`: 현재 로컬 브랜치와 원격 브랜치의 추적 관계 설정
- 이후 같은 브랜치에서는 `git push`만 입력 가능

기능 브랜치 최초 push:

```bash
git push -u origin feature/quiz-play
```

이후:

```bash
git push
```

`push`는 작업 파일을 임의로 보내는 명령이 아니라, 이미 만든 로컬 커밋을 원격 저장소로 보냅니다.

## 6. 브랜치와 병합

### 새 브랜치를 만들면서 이동

```bash
git checkout -b feature/quiz-play
```

- `checkout`: 작업할 브랜치 전환
- `-b`: 새 브랜치 생성
- `feature/quiz-play`: 브랜치 이름

슬래시(`/`)는 폴더가 아니라 브랜치 이름을 보기 좋게 분류하는 관례입니다.

### 기존 `main`으로 이동

```bash
git checkout main
```

커밋되지 않은 변경이 브랜치 이동과 충돌하면 Git이 이동을 막을 수 있으므로 먼저 `git status`를 확인합니다.

### 병합 커밋을 남기며 합치기

```bash
git checkout main
git merge --no-ff feature/quiz-play -m "Merge: 퀴즈 풀기 브랜치 병합"
```

- `merge`: 지정한 브랜치의 변경을 현재 브랜치에 합침
- `--no-ff`: fast-forward가 가능해도 별도 병합 커밋을 남김
- 실행 위치: 합칠 결과를 받을 `main` 브랜치

```text
main ─────●────────●
           \      /
feature     ●────●
```

`--no-ff`는 기능 브랜치가 따로 존재했다는 흔적을 이력에 분명히 남깁니다. 모든 개인 학습 커밋에 반드시 필요한 옵션은 아니며, 과제에서 브랜치 생성·병합 기록을 눈에 보이게 요구할 때 의미가 큽니다.

### 충돌이 난 병합 취소

```bash
git merge --abort
```

병합 도중 `CONFLICT`가 발생했고, 해결 대신 병합 전 상태로 되돌리고 싶을 때 사용합니다. 병합이 진행 중이 아닐 때는 사용할 필요가 없습니다.

### `checkout`과 `clone`의 차이

- `checkout`: 같은 저장소 안에서 작업할 브랜치를 바꿈
- `clone`: 원격 저장소 전체를 실제 새 폴더로 복제

## 7. 원격 변경 가져오기와 복제

### 기존 저장소 최신화

```bash
git pull
```

원격의 새 커밋을 내려받고 현재 브랜치에 통합합니다. 개념적으로 `fetch + 통합`에 가깝습니다. 통합 방식은 설정에 따라 달라질 수 있으므로 작업 전 로컬 변경이 없는지 `git status`로 확인하는 습관이 필요합니다.

대상을 명시하려면:

```bash
git pull origin main
```

### 처음 새 폴더로 받기

```bash
git clone https://github.com/내아이디/python-quiz-game.git python-quiz-game-clone
```

다음을 한 번에 수행합니다.

1. 새 폴더 생성
2. 파일과 커밋 이력 다운로드
3. Git 저장소 구성
4. 원격 저장소를 `origin`으로 등록
5. 기본 브랜치 체크아웃

같은 이름의 비어 있지 않은 폴더가 이미 있으면 실패할 수 있습니다.

간단한 구분:

- 처음 전체를 받는다 → `clone`
- 이미 받은 저장소를 최신화한다 → `pull`
- 내 커밋을 원격으로 보낸다 → `push`

## 9. 미션 2의 18개 커밋 계획

아래는 원래 설계도에서 사용한 커밋 흐름입니다. 실제로 해당 변경이 스테이징된 상태에서만 각 커밋을 만들어야 하며, 메시지만 연속으로 입력해서는 안 됩니다.

1. `Docs: 프로젝트 초기 설정 (README 초안, .gitignore)`
2. `Feat: QuizGame 뼈대와 메뉴, 번호 입력 검증 구현`
3. `Feat: Quiz 클래스 구현 (문제 표시, 정답 확인, 딕셔너리 변환)`
4. `Feat: 기본 퀴즈 데이터 5개 등록`
5. `Feat: 퀴즈 풀기 기능 구현`
6. `Merge: 퀴즈 풀기 브랜치 병합` — 일반 커밋이 아니라 `git merge --no-ff`가 생성
7. `Feat: 퀴즈 추가 기능 구현`
8. `Feat: 퀴즈 목록 기능 구현`
9. `Feat: 점수 확인 기능 구현 (최고 점수 갱신)`
10. `Feat: state.json 저장·불러오기 구현 (손상 복구 포함)`
11. `Feat: 랜덤 출제와 문제 수 선택 추가`
12. `Feat: 힌트 기능 추가 (0으로 보기, 점수 차감)`
13. `Feat: 퀴즈 삭제 기능 추가 (확인 절차 포함)`
14. `Feat: 점수 기록 히스토리 추가`
15. `Refactor: 상수 분리와 주석 정리`
16. `Docs: README 상세 작성`
17. `Docs: 복제 저장소에서 실습 한 줄 추가`
18. `Docs: 실행 스크린샷 추가`

접두어:

- `Feat`: 새 기능
- `Docs`: 문서 변경
- `Refactor`: 외부 동작을 바꾸지 않는 코드 구조 정리
- `Merge`: 브랜치 병합

원문에서 확인된 예시 이력에는 기능 커밋 `87dc418`, 병합 커밋 `e246eba`, 복제본 README 변경 `48ff64a`가 언급되었습니다. 현재 저장소의 실제 해시와 일치하는지는 `git log --oneline --all`로 다시 확인해야 합니다.

## 10. 기능 동작 검증표

### 필수 기능

- [ ] 실행 시 메뉴가 정상적으로 표시된다.
- [ ] 퀴즈 풀기, 추가, 목록, 삭제, 점수 확인 기능이 동작한다.
- [ ] 정답과 오답 판정이 정확하다.
- [ ] 공백, 문자, 범위 밖 숫자, 빈 입력을 처리한다.
- [ ] 프로그램 종료 후 재실행해도 추가한 퀴즈와 최고 점수가 유지된다.
- [ ] 기본 퀴즈가 5개 이상 포함된다.
- [ ] `Ctrl+C` 또는 EOF 상황에서 가능한 범위에서 안전하게 종료한다.

### Git 요구사항

- [ ] GitHub 저장소에 코드가 올라가 있다.
- [ ] 의미 있는 커밋이 10개 이상 존재한다.
- [ ] 브랜치 생성과 병합 기록이 `git log --oneline --graph --all`에 보인다.
- [ ] `clone` 실습을 수행했다.
- [ ] 복제본의 변경을 `push`하고 원래 폴더에서 `pull`해 반영했다.
- [ ] 최종 작업 트리가 `git status`에서 깨끗하다.

### 코드 구조 설명

- [ ] `Quiz`와 `QuizGame`의 책임을 설명할 수 있다.
- [ ] 입력 검증, 게임 진행, 저장·불러오기 로직의 분리 기준을 설명할 수 있다.
- [ ] `state.json`을 읽고 쓰는 위치와 실행 순서를 설명할 수 있다.
- [ ] 커밋을 어떤 단위로 나눴는지 설명할 수 있다.
- [ ] 커밋 메시지 규칙을 설명할 수 있다.
- [ ] 주요 주석의 대상 코드와 이유를 설명할 수 있다.

## 14. 별도 메모: AI 제품 실험 원칙

원문에 섞여 있던 제품 실험 메모는 프로젝트 학습과 직접 관련이 없으므로 다음 원칙만 보존합니다.

- 여러 제품을 동시에 만드는 물량공세보다 하나의 공통 엔진으로 가설을 빠르게 바꾸는 실험 물량공세가 낫다.
- 한 실험의 제작 시간을 제한하고, 남은 시간을 실제 사용자 노출과 판매에 사용한다.
- 초기에는 통계적 확증보다 다음 주를 더 투자할 신호가 있는지 판단한다.
- 예시 운영 기준: 표적 사용자 30회 직접 노출 또는 자격 있는 방문 100회, 핵심 행동 10명, 일주일 내 재사용 3명, 실제 결제 1명.
- 결제만 있고 재사용이 없으면 일회성 서비스일 수 있다.
- 재사용은 있으나 결제가 없으면 가격, 신뢰, 대체재를 점검한다.
- 아무 신호가 없으면 기능을 더 만들기보다 고객군이나 약속을 바꾼다.
- 저가는 영구 포지셔닝이 아니라 유료 검증 가격으로 사용한다.
- 장기적으로는 기능뿐 아니라 유입 채널과 반복 가능한 배포 기반을 확보해야 한다.

원문의 외부 통계와 연구 언급은 이 파일 안에 출처가 온전히 남아 있지 않아, 검증 없이 수치 근거로 재사용하지 않습니다.
